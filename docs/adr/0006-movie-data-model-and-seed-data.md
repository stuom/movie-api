# ADR-0006: Movie data model and seed data

- **Status:** Accepted
- **Date:** 2026-10-13
- **Updated:** 2026-10-13 (all fields are searchable, see ADR-0007; no extra search fields are stored; re-seeding after deleting every movie made explicit); 2026-10-13 (slice 02: frozen normalization and id algorithm, Unicode NFC, edge rules; rules live in `MovieRules`, ADR-0009); 2026-10-13 (slice 05: no control characters in names, genres and person names); 2026-10-14 (slice 06: seed failure policy and partial-seed limitation); 2026-10-14 (slice 09: the sample data is seeded exactly as provided, see the last consequence)

## Context
The user provided a sample dataset (`movies-compact.json`, 20 movies) that defines the shape of a movie: `name`, `year`, a list of `genres`, `ageLimit`, `rating`, a `director` (first and last name), a list of `actors` (first and last name) and a `synopsis`. The dataset is also the natural content for a demo deployment. It contains typos and likely wrong values (for example the genre "Familty") and stray whitespace in names.

## Options considered
1. **Normalize into collections** (movies, people, genres) with references: avoids duplication, but every movie read needs several more reads, which costs free-tier quota, and relations are awkward in Firestore.
2. **Embed everything in the movie document:** one read per movie, simple to map, some duplication of person names (acceptable at this scale).
3. **Keep the dataset's vocabulary** (`name`, `year`) or rename to `title`, `releaseYear`: keeping it means the sample file doubles as an example request body.
4. **Genres as a fixed enum vs free text:** an enum would reject the typo "Familty" but needs a maintained vocabulary and a migration story. Free text is simpler for now.
5. **Seed directly into the database vs through the service:** going through `MovieService.createMovie` gives seed data the same validation, trimming and duplicate detection as API input.

## Decision
- A movie is one Firestore document with embedded `director` (a `Person`), `actors` (list of `Person`) and `genres` (list of strings), using the dataset's field names. No derived search fields are stored; text is normalized in memory when searching (ADR-0007).
- Validation: `name` 1-200 chars, `year` 1888..current year + 5, `genres` 1-5 entries of 1-50 chars, `ageLimit` 0-18, `rating` 1-5, `actors` at most 30, `synopsis` at most 2000, person names 1-100 chars. All text is trimmed. Names, genres and person names must not contain control characters (`Character.isISOControl`: U+0000-U+001F, U+007F-U+009F); the synopsis may, so it can hold line breaks. The rules are enforced in one place, `MovieRules` (ADR-0009).
- Genres are free text for now.
- The document id is a deterministic hash of normalized `name` + `year`. It also enforces uniqueness: Firestore's `create` fails when the id already exists, so duplicate detection is atomic without a transaction, and the failure is returned as `409 Conflict`.
- **Normalization (frozen, `TextNormalization.normalize`):** Unicode NFC, then `String.strip()`, then collapse every run of `\p{javaWhitespace}` to one space, then `toLowerCase(Locale.ROOT)`. Whitespace means `Character.isWhitespace` everywhere, so the non-breaking space U+00A0 is *not* whitespace (a name of only NBSPs is accepted). Accents are not folded. NFC makes a precomposed "é" and "e" + combining accent give the same id.
- **Id (frozen, `MovieId.derivedFrom`):** the first 32 lowercase hex characters of SHA-256 over the UTF-8 bytes of `normalize(name) + "|" + year`. Golden values, computed outside the code with `printf 'aliens|1986' | sha256sum | cut -c1-32`: "Aliens"/1986 -> `53e87be920fdef6e6176fa0c355406d8`, "Amélie"/2001 -> `40454ad510a87b6065b4b150928b2b65` (pinned in `MovieIdTest`). Changing either algorithm means migrating every stored id.
- **Edge rules:** stored text is only `strip()`-trimmed (no NFC, no case change). Length limits count `String.length()` (UTF-16 units) of that trimmed text. "Required" means non-null and non-blank after trimming. A blank `synopsis` becomes `null`; missing `actors` become an empty list. Genres that differ only by case are allowed. The control-character check runs on the trimmed text: control characters that are whitespace (tab, line feed, carriage return, U+001C-U+001F) are trimmed from either end like spaces, any other control character (NUL, ESC, DEL, U+0085, ...) is rejected wherever it appears, even at an end. A value made only of such characters (for example `"\u0000"`) is not blank, so it is reported as `must not contain control characters`, not `is required`. The violation is reported in addition to a length violation.
- Sample data is stored at `src/main/resources/seed/movies.json` and loaded by `MovieSeedLoader` on startup when `app.seed.enabled=true` and the loaded catalog is empty. Entries go through `MovieService.createMovie`, converted one at a time with the strict application mapper (ADR-0012). An entry that cannot be converted, breaks a rule or is a duplicate is logged at WARN with its index and skipped. A storage failure (`MovieStorageException`) stops seeding: it is logged and startup continues, because waiting up to 20 seconds for each of 20 entries would exceed Cloud Run's 240-second startup limit. An unreadable, empty or non-array seed file fails startup (it ships in the jar, so that is a build defect). A summary is logged at the end.
- The API only lists, searches and adds movies: no update and no delete endpoint. The service is deployed unauthenticated, so write access is limited to creating new movies. Corrections and removals are done by hand in the Firestore console (after which the catalog reloads within the refresh interval).
- Suspected mistakes in the dataset are reported to the user, not silently corrected.

## Consequences
- Reading or listing movies never needs joins; the cost is one read per movie.
- The same person appearing in several movies is stored several times; renaming a person means updating every movie. Acceptable for this scope.
- Free-text genres allow inconsistent spellings ("Sci-fi" vs "Science Fiction"). A controlled vocabulary or a genre endpoint can be added later with a new ADR.
- Actors, director and synopsis are searched in memory (ADR-0007), so adding a filter on any field needs no schema or index change.
- The seed file doubles as an example of a valid request body and as test material.
- Deleting every movie by hand brings the sample data back on the next startup, because the catalog is then empty. Set `app.seed.enabled=false` if that is unwanted.
- A seed run stopped part-way by a storage failure is not resumed: the catalog is no longer empty on the next startup, so the remaining entries are never added. To re-seed, delete the seeded movies in the Firestore console and restart.
- Seeding runs after the web server listens, so early requests may see a partly seeded catalog.
- The control-character rule applies to new movies only: stored movies are not re-validated when the catalog loads (ADR-0009). A stored movie with control characters stays loadable and must be fixed by hand in the Firestore console. The seed file contains none. Normalization and the id algorithm are unchanged.
- Unicode line and paragraph separators (U+2028, U+2029) and format characters such as bidi overrides (U+202E) or zero-width spaces are not ISO control characters and are still accepted in names; whether to reject them is an open question for the user.
- **Seed as provided (user decision, slice 09):** the first deploy seeds `movies.json` exactly as provided. The suspected mistakes listed in AI log 06 (for example Avengers: Endgame as 2018, "Downtown Abbey", the genre "Familty") are stored permanently: there is no update or delete endpoint, so they can only be fixed by hand in the Firestore console. Fixing them in the seed file later has no effect on a database that is already seeded. The first-deploy seed check and recovery are in `docs/deployment.md`.
